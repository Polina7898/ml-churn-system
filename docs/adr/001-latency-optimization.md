# ADR-001. Оптимизация времени отклика сервиса предсказания оттока

**Статус:** Принято
**Дата:** 28.05.2026
**Автор:** Кузнецова П. Г.

## Контекст

Текущая версия Churn API (v1) использует in-process инференс GradientBoosting и работает синхронно. Снятые на продакшене метрики латентности дают среднее время отклика 3.5 с при стандартном отклонении 0.4 с, что не укладывается в SLO `latency p95 < 200 мс`.

Команда предлагает архитектуру v2: модель экспортируется в ONNX, инференс выполняется через `onnxruntime`, добавлен LRU-кэш признаков для повторных запросов по одному клиенту. На стенде нагрузочного тестирования сняты данные по обеим версиям объёмом по 500 000 наблюдений.

Перед принятием решения нужно убедиться, что улучшение не случайное.

## Гипотезы

- **H0:** распределения времени отклика существующей (v1) и улучшенной (v2) систем одинаковы (средние не отличаются)
- **H1:** распределения отличаются, улучшенная система быстрее

## Метод

- основной критерий, Mann-Whitney U (двухсторонний, непараметрический, устойчив к выбросам)
- дополнительный, Welch t-test для подтверждения
- уровень значимости α = 0.05
- размер выборок n = 500 000 для каждой системы
- скрипт: `src/mdd_analysis.py`

## Результаты

| Метрика | v1 (текущая) | v2 (улучшенная) |
|---|---|---|
| Среднее | 3.500 с | 2.000 с |
| Медиана | 3.500 с | 2.000 с |
| p95 | 4.158 с | 2.659 с |
| Стандартное отклонение | 0.400 с | 0.400 с |

| Тест | Статистика | p-value |
|---|---|---|
| Mann-Whitney U | ≈ 2.43 × 10¹¹ | < 1e-300 |
| Welch t-test | t ≈ 1873.5 | < 1e-300 |
| Cohen's d | ≈ 3.747 (очень большой эффект) |, |

## Decision

p-value << α = 0.05, **H0 отклоняем**. Различия между распределениями времени отклика статистически значимы, эффект очень большой (Cohen's d ≈ 3.75).

Принимаем решение: **внедряем архитектуру v2 в продакшен** через канареечный релиз с переключением трафика 10% → 50% → 100%. Откат, автоматический при нарушении SLO `error rate < 1%` или `ROC-AUC < 0.82`.

## Последствия

Положительные:
- сокращение среднего времени отклика на 43% (с 3.5 с до 2.0 с)
- разгрузка CPU за счёт онлайн-кэша признаков
- ближе к целевому SLO p95 (потребуется ещё одна итерация, батчинг запросов)

Отрицательные и риски:
- появляется CI-шаг конвертации модели в ONNX
- холодный старт после рестарта, кэш признаков пуст, первые ~1000 запросов медленнее
- зависимость от `onnxruntime`, нужно следить за обновлениями

## Дальнейшие шаги

- следующий ADR, переход на батчинг запросов для достижения p95 < 200 мс
- обновление SLI/SLO с пересмотренным таргетом по `latency`
